# Boshsu 1.2 RC5 — Windows discovery and recorder research

## Outcome

RC5 adds documented Windows application registration and a stable process identity. This is a real client-side improvement for software which discovers applications from Windows records. It is **not a verified AMD/Insights automatic game-detection fix**. The previous window audit and manually added AMD entry did not establish automatic recognition.

On a normal packaged `Boshsu.exe` startup, the client assigns `Bosh.Boshsu` through `SetCurrentProcessExplicitAppUserModelID` before presenting UI. With registration enabled, it registers this executable under the current user's App Paths and Applications keys and creates a Start-menu shortcut with the same AppUserModelID, target, working directory and icon. The main window has its Boshsu name from construction rather than waiting for the later scheduled title update.

Registration runs before the game loop, not per frame or on an input thread. Existing owned entries are updated only when necessary. A later launch from a moved/different copy can update the registered target; disabling an older copy cannot remove a newer copy's registration. Foreign installer entries and unreadable/unowned shortcuts are retained. Registration errors appear on the integration page and do not stop gameplay startup. Source/test executables and qualification packages skip persistent registration.

Options → Advanced → Windows integration exposes the saved On/Off preference, status and repair action. Universal search finds Windows registration, game detection and recording. Disabling removes this copy's owned registration; it does not change profiles, scores, the AMD profile added previously, or recorder settings. The same implementation is included in personal and clean packages.

## Research findings

- Microsoft documents per-user App Paths and Applications registration for identifying and locating desktop applications. It does not claim these entries add an application to a third-party game catalogue. [Application registration](https://learn.microsoft.com/en-us/windows/win32/shell/app-registration).
- Microsoft recommends an explicit AppUserModelID and specifies that the process and its shortcut should use the same ID. This identifies the application to Windows; it is not a game-classification or recording API. [AppUserModelIDs](https://learn.microsoft.com/en-us/windows/win32/shell/appids), [startup identity API](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-setcurrentprocessexplicitappusermodelid).
- AMD documents automatic scanning and a separate manual Add A Game workflow. The personal client was successfully added with its actual name, icon and executable path in the preceding task. That proves local profile acceptance, not recognition on another machine. [AMD application profiles](https://www.amd.com/en/resources/support-articles/faqs/DH3-012.html).
- AMD's ADL SDK includes driver application-profile creation and assignment APIs. Their documentation concerns driver-area/property records, and does not promise registration in Radeon Software's game library or a recorder's support catalogue. RC5 does not guess driver-area/property names or overwrite graphics profiles to try to force detection. [AMD ADL application-profile APIs](https://github.com/GPUOpen-LibrariesAndSDKs/display-library/blob/master/Public-Documents/html/group__APPPROFILESAPI.html), [ADL scope](https://github.com/GPUOpen-LibrariesAndSDKs/display-library/tree/master/Public-Documents).
- AMD separately documents an OpenGL recording limitation: its Record Desktop path is available for OpenGL in windowed mode. Boshsu's qualified renderer is OpenGL. Windows registration does not remove this API-specific capture limitation. [AMD recording documentation](https://www.amd.com/en/resources/support-articles/faqs/DH3-023.html).
- Insights documents supported-game selection and acknowledges unsupported games as a possible reason recording fails; its current website advertises manual capture for unsupported games. No general client self-registration SDK/API was found in the reviewed public Insights documentation. Automatic match/highlight events are a further integration, not a consequence of setting a window title. [Insights help](https://insights.gg/help/en/articles/13765168-why-isn-t-insights-capture-working), [Insights Capture](https://insights.gg/).
- The old Windows Games Explorer/GDF mechanism is unavailable on Windows 10 version 1803 and later, so it is not a modern solution. [Microsoft Games Explorer documentation](https://learn.microsoft.com/en-us/windows/win32/dxtecharts/windows-game-explorer-integration).

There is no universal documented “recognise this as a game in every recorder” flag in the reviewed sources. Registration is implemented without impersonating osu!, changing executable names to match other games, editing private recorder databases or replacing the McOsu renderer.

## Supplied Bosh MaxAssist comparison

The supplied personal MaxAssist package still runs as `osu!.exe`; its ProductName, FileDescription and OriginalFilename are all `osu!`/`osu!.exe`. Boshsu runs as `Boshsu.exe` and its ProductName/FileDescription are Boshsu. Its internal assembly filename remains StableRemastered for compatibility with existing managed modules.

The OpenTK DLL in both installed packages is byte-identical. The supplied frontend's WindowsGameHost already renders through `Window.Form`, with the same WinForms/OpenGL host and FadeGLControl construction retained by Boshsu. The old package's saved CompatibilityContext is Off, selecting the normal OpenGL path. No separate recorder/game-discovery SDK layer was found in the inspected supplied window, startup and MaxAssist/bootstrap sources.

The supplied old Uninstaller helper does register installed-application information, but it does so under osu!'s identity, publisher and uninstall records. Copying that function unchanged would claim or modify the existing osu! installation. RC5 instead adds Boshsu-owned, per-user Windows registration and a matching shortcut.

Recognition of the old MaxAssist client through its known osu! identity is a plausible explanation, not a proven account of AMD/Insights' private detection algorithms. Reusing its window layer is already the current design; copying it again would not establish recorder recognition.

## Validation and limits

29 non-GUI Windows registration checks passed using a disposable registry subtree and workspace shortcuts. They exercise the actual Windows AppUserModelID API, registry writes, persisted Shell Link properties, idempotence, Unicode/spaces, moving between copies, opt-out persistence, performance-profile independence, damaged-shortcut opt-out, foreign-entry preservation and test-host exclusion. The restricted sandbox initially denied registry writes; the isolated checks then passed with authorised host access and removed their own test subtree. The repeat-run fixture now uses a fresh workspace directory so intentionally retained corrupt shortcuts cannot contaminate the next run.

The managed solution build passed with existing warnings. Final package/regression results are recorded beside the candidate. Automatic discovery, capture hooks and recording performance remain unverified, including Insights on another person's computer. The native engine, renderer maths, assist model, PP rewards and gameplay timing are unchanged.

Windows registration is enabled on first launch of the new packaged build and can be disabled in Options. It supplies documented application discovery information; whether a particular recorder uses it requires that recorder's confirmation or a real compatibility check. Public release notes must retain this distinction.

## Manual updates and first-time installation

Launching `Boshsu.Updater.exe` without arguments now opens a normal Windows manual-update window. Choose the existing Boshsu.exe, complete clean release ZIP and SHA256SUMS.txt from the same official release. Full archive and individual-file verification runs away from the UI thread. The same protected-path, staging and rollback installer used by in-client updates preserves profiles, scores, maps, skins and settings. A separate helper waits for the manual updater to exit, so the installed updater can itself be replaced. The target game must be closed; unrelated installations can remain open. Source ZIPs, missing/mismatched checksums, foreign installations and downgrades are rejected. Manual updates require no network or GitHub login. Local checksums are integrity checks, not a publisher signature.

82 updater checks passed, including the manual path, newer/same/older versions, source ZIP rejection, bounded helper staging, failed preparation cleanup and protected player data. Existing tests retain rollback/failure coverage. First-time players use the complete portable clean ZIP, extract every file to a writable folder and run Boshsu.exe; the updater is for existing installations. Windows x64 and .NET Framework 4.8 remain required. The candidate is prepared separately; the user's running personal RC4 installation is not replaced.

The complete release ZIP was extracted into a new folder without saved settings/accounts. The production executable passed eight first-launch assertions (Main Menu, fresh profile/no scores, fullscreen/native-resolution/primary-display configuration, saved display edits) and five restart assertions. A launch-only test-display override kept the actual window on the user's left monitor, while validating the normal primary-display defaults. An owned synthetic Standard map then completed one native gameplay cycle, four pause/resume pairs and one retry, returning Results and closing cleanly. These automated runs qualify launch/lifecycle on this Windows PC, not every machine or physical input/capture compatibility.

The standalone updater was actually opened without arguments from the extracted package. Its native file picker selected the full clean ZIP and adjacent checksum file. Verification, confirmation, separate-helper installation and automatic client restart succeeded while the separate personal client remained open. Thirteen tracked account/score/map/settings files were byte-identical afterward; the saved-display restart assertions passed again. The personal executable retained its RC4 hash. Final package sealing changes documentation/metadata only; executable, updater and native runtime hashes must match those exercised by this launch/update run. Evidence is retained locally in `evidence/windows-discovery/` and is excluded from source/player packages.
