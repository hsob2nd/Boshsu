# Build, test and release ownership

`tools/Build.ps1` discovers installed build tools, restores exact supplied binary dependencies, prepares the pinned native compiler/library sources and builds the two runtime outputs. Its default is two build jobs. Build artifacts remain under `_build` and the imported projects' `bin/obj` folders. It never installs over a player folder.

The pipeline also compiles the source-owned `UltimatePersonalModel.dll`. Its relative output paths are resolved before changing the compiler working directory. On the qualified Windows toolchain, rebuilding from the fresh source extraction produced the exact sealed model SHA256 `b636fe27c4dc34bfd7a3dcf032b67dc9e43bc744fc80c073125fa4b57aecaa7e`. Keep the supplied qualified `.pgold` data from the matching runtime or source archive with the staged client; it is not replaced with a newly trained model. A different compiler's output still needs qualification before distribution.

`tools/Test-Release.ps1` creates a fresh disposable binary copy. CPU assertions cover contracts, snapshot ABI/fidelity, layout, offline presentation, transactional updates and recurring allocation overhead. Real-window gameplay, device feel, audio and long-session qualification remain separate. Never run historical personal migration/restoration tools as a general release procedure.

Run `tools/Test-Accounts.ps1 -Runtime <matching-portable-folder>` for source-compiled account/provider tests. The matching portable folder must include `PPProviders/akatsuki-b96019f.zip` and `PPProviders/ccv3-pp-main.zip`; tests copy those shipped packages into their disposable fixture directory. Private development evidence/reference paths are never test dependencies. The hosted CPU script supplies this runtime explicitly.

`tools/archive_source.py` packages application/contract/provider/personal sources, the modified McOsu integration, original pinned McEngine source and bundled dependency archives, tests, current documentation and the supplied qualified model data. It excludes private evidence, checkpoints, player data, binary outputs and obsolete personal staging scripts. Hash verification must pass for every pinned McEngine input before archiving and inside the final ZIP. Retain GPL/MIT/OFL and supplied-dependency notices.

Release candidates need a complete clean portable ZIP, matching corresponding source ZIP and `SHA256SUMS.txt`. Use `stage_release.py` with the sealed baseline's exact SHA256 and new build outputs, then `archive_source.py` with the qualified model data, and `seal_release.py` with that fresh staging folder/source ZIP. Each tool refuses an existing output destination. The sealer validates clean manifest coverage, rejects user/development data, binds the corresponding source hash and includes the qualification reports. Verify fresh launch, prior-updater compatibility, preservation/rollback on a copied installation and privacy before publishing. Do not edit a player's live folder to perform package qualification. Build success and checksum verification are not gameplay certification.

The release workflow template is in `tools/ci`. Deploy it to `.github/workflows/release-integrity.yml`, with `verify_release.py` and `run_cpu.ps1` under `.github/scripts` in the public repository. It has read-only repository permissions. Its Linux job verifies GitHub asset digests, archive/member hashes, clean data separation, required portable files and corresponding pinned native source without executing the downloads. A dependent Windows job runs portable-host contract/navigation/update fixtures and source-compiled account/PP-provider fixtures from matching checksum-verified inputs. It supports published-release events and a manual tag input. Complete source builds and Windows/OpenGL/physical-device gameplay qualification remain separate.

The template follows the current official [checkout](https://github.com/actions/checkout) and [setup-python](https://github.com/actions/setup-python) usage. Report a workflow as installed or passed only after observing the actual repository/run; the template alone is not CI evidence.
